# 改善ブレスト（定期的に何周も回す）

根本: 通勤通学の時間が憂うつ → 小さな楽しみと便利さ。考える順番は必ず **メリット → それを叶える機能**（ユーザー指定）。
判断の軸: 入力を増やさない／ぱっと見でわかる／報告したくなる（＝空いてる号車の精度が上がる）。

## いまの意見まとめ（優先順）

1. **色覚の多様性: 混み具合が色だけで区別できない**【計算で確認・重要】5 段階の色（--l1〜--l5）は白文字の読みやすさをそろえたため明るさがほぼ同じ（相対輝度 0.11〜0.16）。2 型色覚（日本人男性の約 20 人に 1 人）の見え方に変換すると 5 色とも同じようなオリーブ色になる。電車の図は号車ごとの混み具合を色だけで表しているので、その人には読めない → 号車のマスに混み具合の数字（1〜5）か記号を小さく入れ、色は明るさにも差をつける。手間: 小 / 効果: 大
2. **地方の短い編成（1〜3 両）が選べない**【コードで確認・不具合に近い】「何両編成？」の候補が 4 両から（app.js の CAR_COUNTS）。2 両のワンマン線の人は「わからない」= 10 両になり、ない号車をすすめる。1〜2 両だと全号車が同点で「1号車・2号車が空いてそう」と意味のない表示 → 候補に 1・2・3 両を足し、2 両以下は「号車の差は小さい路線です。空いてる時間帯を見る」に切り替える。手間: 小 / 効果: 大（地方の人には必須）
3. **ストアのスクリーンショットが v1 のまま**【ファイルで確認】docs/store/screenshots の 3 枚は 10/2 10:59 撮影（号車の機能を入れる前）。説明文は「空いてる号車」なのに画像は時間帯の記録画面で、初めて見る人に伝わらない → 今の画面で撮り直す（エミュレータで撮れる。差し替えのアップロードはユーザー）。手間: 小 / 効果: 大
4. **機種変更（書き出し→読み込み）で共有番号が変わる**【コードで確認】書き出しファイルには端末 ID が入るが、読み込み（parseBackup）は路線・記録・メモだけを取り込み ID を捨てる → 新しい機種では別人扱いになり、ランキング・「役に立った人数」・削除依頼の番号が途切れる → 読み込みで共有番号も引き継ぐ。手間: 小 / 効果: 小〜中（Android は OS の自動バックアップで復元されるので、主に Web 版・iPhone 向け）
5. **初めて開いた人が、何をすればいいかわからない** → 初回だけ路線選びのシートを自動で開き、選び終えたらすぐ「空いてる号車」を見せる。共有のお願いは 1 回記録してから。手間: 小 / 効果: 大
6. **押すところが小さい**【画面で確認】号車ボタン 40×40、「くわしく」32px 高、「◯両編成（変える）」36px 高、凡例の文字 12px。揺れる車内・片手・手袋では押し間違える → 押せる部分を 44px 以上、凡例を 13〜14px に（見た目はほぼ同じ）。手間: 小 / 効果: 中
7. **通知から直接報告**（アプリを開かずに混み具合を 1 タップ）→ ローカル通知のアクションボタン（Capacitor の actionTypes）。手間: 中 / 効果: 大
8. **3〜4 か月で称号が打ち止め**【コードで確認】最上位「伝説の運転士」は 3000pt。1 日 2 回記録だと約 3.5 か月で届き、その先の目標がない → 月ごとにリセットされる「今月の目標」（例: 今月 30 回）と季節のバッジ。入力なし。手間: 小 / 効果: 中
9. **最初はみんな「推定」だらけで価値が出るまでが長い** → 公開は 1〜2 路線に絞って告知し、路線ごとに「報告◯件で★2」の進み具合を見せる。手間: 小〜中 / 効果: 中〜大

済み:
- ✅（2026-10-03 対応: 路線選びの最後に「何両編成？」、空いてる号車の欄から変更）**両数（何両編成か）が全員 10 両のまま**【不具合に近い】大江戸線（8 両）や山手線（11 両）で、ない号車をすすめたり端を間違えたりする → 路線を選んだ直後に「何両編成？」を 1 タップで聞く（よくある両数を候補に）。手間: 小 / 効果: 大

## 周回ログ

### 第 1 周（2026-10-03）視点: 初めて開いた人 / 毎日乗る会社員（3 か月目）/ 運用・サーバー
**初めて開いた人**
- メリット「30 秒で自分の路線の空いてる号車が見える」→ 初回だけ路線選びを自動で開く。いまは「いつもの路線」（路線情報なし）のまま推定が一般論しか出ない
- メリット「何両編成か知らなくても正しくすすめてくれる」→ 路線選択の最後に両数を聞く（候補ボタン）。いまは乗換メモの画面の中でしか変えられない（コードで確認: app.js の memo ステップ）
- メリット「いきなり同意を求められない」→ 共有のお願いカードは 1 回記録したあとに出す（いまは最初から一番上に出る）

**毎日乗る会社員**
- メリット「開かなくても答えと報告が済む」→ 通知にアクションボタン（ガラガラ／ふつう／混んでる）。朝の一言通知（実装済み）と組み合わせると、通知だけで完結する
- メリット「並ぶ場所まで迷わない」→ 号車だけでなく乗車位置（ホームの番号）。駅ごとのデータが必要で重い → 乗換メモで代替し、需要を見て
- メリット「帰りも同じ手間で使える」→ 時間帯で行き/帰りの路線自動切り替え（実装済み）。帰りの路線の追加を初回に促す

**運用・サーバー**
- 閲覧記録（views）はアプリを開くたびに 1 回書き込む。D1 無料枠は 1 日 10 万書き込み → 1 日 1 万人 × 数回までは大丈夫。超えそうなら「1 端末 1 日 1 枠 1 行」はそのままに、書き込みを 1 日 1 回にまとめる
- 報告が少ない路線は推定のまま → ローンチは路線を絞る（宣伝の話。アプリ側は路線ごとの「報告の集まり具合」表示で後押し）

### 第 2 周（2026-10-03）視点: 学生 / 子連れ・ベビーカー・車いす / 圏外・オフライン（地下鉄）
**学生**
- メリット「友だちと同じ号車で会える／待ち合わせが楽」→ 空いてる号車の欄に「LINE で送る」（例:「明日 7:40 の 7 号車で」）。Web は navigator.share、アプリは @capacitor/share の追加が必要。手間: 中 / 効果: 中（口コミで広がる入口にもなる）
- メリット「試験期間は空き方が違うのを知りたい」→ 試験・休暇モードは「くわしく」に移した。年数回しか使わないので位置としては妥当。季節で自動提案（2月・7月に一言）は余地あり。手間: 小 / 効果: 小
- メリット「ランキングで友だちと競える」→ 路線ランキングは実装済み。友だち同士の比較は ID 交換が要り入力が増えるので見送り

**子連れ・ベビーカー・車いす**
- メリット「エレベーターに近くて、空いている号車がわかる」→ 乗換メモの「エレベーター」タグはもうある。設定で「ベビーカー・車いす優先」を 1 回オンにすると、おすすめを「エレベーター近く × 空いてる」で選ぶ。データは自分のメモだけなので、メモがない人には効かない。手間: 小〜中 / 効果: 中（必要な人には大）
- メリット「優先席・フリースペースのある号車を知りたい」→ 車両ごとの設備データが要る。公開データが見当たらないので、みんなの報告に「フリースペースあり」を付けられる案。入力が増えるので保留

**圏外・オフライン（地下鉄）**
- 記録は端末に保存し、報告は送れなくても次に通信できたとき送る（online / 画面復帰で再送）＝ コードで確認、問題なし
- メリット「圏外でも表示を信じていいか分かる」→ みんなの集計が取れないと、黙って自分の記録と傾向だけの表示に戻る。根拠の一文（「みんなの報告 ◯件…」）が消えるだけなので、気づけない → 取れなかったときは「いまは圏外のため、あなたの記録と一般的な傾向だけで表示」と一言。手間: 小 / 効果: 小〜中

**アクセシビリティ（画面で確認）**
- 押せる部分の高さが 44px 未満のものがある（号車 40px、「くわしく」32px、「◯両編成（変える）」36px）。凡例は 12px でうすい灰色 → 上の意見まとめ 4 へ

### 第 3 周（2026-10-03）視点: 3 か月使った人 / プライバシー重視の人 / 競合アプリとの違い
**3 か月使った人**

- メリット「自分の通勤が良くなった実感」→ ふりかえりに「先月より空いてた回数 +3」のような前月比を 1 行。手間: 小 / 効果: 小〜中
- メリット「画面が長くて下まで見ない」→ 下の「今日のおすすめ（時間帯）」「曜日×時間の傾向」は v1 の機能で、いまの主役（号車）と離れている。たたむか、空いてる号車の欄に「15 分ずらすと ◯号車まで空く」と一言でまとめる。手間: 中 / 効果: 中

**プライバシー重視の人**
- 共有オフなら通信しない（loadShared・loadHelped・loadRank はすべて data.share を見る）＝ コードで確認、問題なし
- メリット「足跡を残したくない時にリセットできる」→ 共有番号はずっと同じ（app.js: data.device は一度作ると変わらない）。「番号を作り直す」ボタンで、以後は別人として扱う（過去の報告は削除依頼で）。手間: 小 / 効果: 小（安心感は大きい）
- メリット「何を送っているか自分の目で見られる」→ データ欄に「送信待ち ◯件」と、送る中身の見本を 1 件表示。手間: 小 / 効果: 小

**競合アプリとの違い**（事実関係は公開前に要確認）

### 第 4 周（2026-10-03）視点: 地方の路線 / 高齢者 / 鉄道会社・収益
**地方の路線**
- 【不具合に近い】「何両編成？」の候補が 4・6・8・10・11・12・15 両だけ（app.js CAR_COUNTS）。1〜3 両の路線は選べず、「わからない」で 10 両扱いになる
- 【表示】carPrior を実際に計算すると、2 両は [2.2, 2.2] で同点、1 両は [3.4] → 「1号車・2号車が空いてそう」「1号車が空いてそう」と、何も言っていない表示になる
- メリット「短い編成でも役に立つ」→ 2 両以下は号車ではなく「何時台が空いてる」（v1 のおすすめ時間帯）を主役に切り替える。ワンマンの「前の車両は降りる人が集まる」などの傾向は、報告がたまれば自然に出る。手間: 小 / 効果: 大
- メリット「本数が少ないので 1 本の判断が大きい」→ 15 分枠の集計は 1 時間に 1〜2 本の路線でも動く（前後 1 枠を半分の重みで足すので）。問題なし

**高齢者**
- メリット「字が小さくても読める」→ 端末の文字サイズ設定に追従するか要確認（rem 指定が多いので概ね追従）。凡例 12px・補足の灰色文字はうすい → 第 2 周の「押すところが小さい」と一緒に直す
- メリット「混み具合の言葉が直感的」→「ガラガラ／座れる／立つけど余裕／混んでる／ぎゅうぎゅう」は色と数字つきで分かりやすい。そのままでよい
- メリット「優先席に座れそうかを知りたい」→ 優先席の位置は車両で違いデータがない。報告に足すと入力が増えるので見送り

**鉄道会社・収益**
- 鉄道会社にとってのメリット「混雑の分散（空いている号車・時間への誘導）」→ 号車ごと・時間ごとの集計（個人が分からない形）は、将来の連携や公開データの材料になる。今は人数が足りないので、話を持っていくのは報告が集まってから
- 収益: サーバーは無料枠で足りる見込み（第 1 周）。広告はプライバシーの方針（外部サービスを入れない）と合わないので入れない。続ける費用が出てきたら「応援（寄付）」のような任意の支払いが候補。課金はストアの手続きと手数料が要るので、必要になってからユーザーと相談

### 第 5 周（2026-10-03）視点: ストア審査・掲載 / 満員電車の会社員 / いたずら・なりすまし
**ストア審査・掲載**
- 【ファイルで確認】ストア用スクリーンショット 3 枚（android-1-record / 2-recommend / 3-memo-remind）は 10/2 10:59、v2 の号車機能より前。フィーチャーグラフィック（10/2 14:48）も v1 の文言の可能性 → 今の画面で撮り直し。手間: 小 / 効果: 大（ストアで最初に見られるのは画像）
- プライバシーポリシーへのリンクはアプリ内（フッター）にある、共有は聞いてからオン、通知の許可はリマインドを設定したときだけ聞く ＝ 問題なし
- アカウントがないので「アカウント削除」の要件はかからない。報告の削除は共有番号で依頼（実装済み）
- 気分・ニックネームは選択式で自由入力がないので、投稿の監視（UGC ポリシー）の対象になりにくい ＝ 入力を増やさない方針がここでも効いている

**満員電車の会社員**
- メリット「ぎゅうぎゅうでスマホを出せない日も記録できる」→ 降りてから記録すると時刻がずれる。いまは「くわしく」の中で -5 分などを押す必要がある → 記録後のメッセージに「乗ったのは 10 分前？」の 1 ボタン（押したら時刻を直す）。手間: 小 / 効果: 中
- メリット「並ぶ位置を変えるだけで楽になる」→ 空いてる号車と乗換メモの階段・出口を 1 行で一緒に出す（「1号車：空いてそう／降りる駅の階段からは遠い」）。メモがある人だけ。手間: 小〜中 / 効果: 中
- メリット「ロック画面のまま報告」→ 第 1 周の「通知から直接報告」と同じ。満員電車では特に効く

**いたずら・なりすまし**（コードで確認）
- 端末 ID はアプリが作るランダムな文字列なので、悪意のある人はいくらでも別人になれる。いまの対策（同じ号車 5 分に 1 回・1 日 30 件・1 台の重み上限・外れ値の保留）は「1 台から大量」には効くが、「ID を変えて大量」には効かない（worker.mjs に IP での制限はない）
- → IP アドレス（Cloudflare の CF-Connecting-IP）を**ハッシュにして日付と混ぜたもの**で 1 日の報告数を制限。IP そのものは保存しない。プライバシーポリシーに一言追加が必要。手間: 小 / 効果: 中（利用者が増える前に入れておくと安心）

### 第 6 周（2026-10-03）視点: 色覚の多様性 / 予想の正直さ / 通勤の憂うつ（根本）
**色覚の多様性**（計算で確認）
- 混み具合の 5 色 #15803d / #4d7c0f / #a16207 / #c2410c / #b91c1c は、相対輝度が 0.159 / 0.160 / 0.163 / 0.153 / 0.112 とほぼ同じ（白文字のコントラストをそろえた結果）
- 2 型色覚のシミュレーション（Machado 2009）では #756c42 / #7b6e1d / #85760a / #877800 / #776a12 となり、5 段階の見分けがつかない
- 記録ボタンは数字と言葉つきなので押すのは困らない。困るのは **電車の図**（号車のマスは号車番号と★だけで、混み具合は色だけ）と曜日×時間の表
- メリット「色が分からなくても空いてる号車が読める」→ マスに混み具合の数字を小さく添える／空いてる号車は太枠（いまもある）に加えて「空」の文字。色は明るさの差もつける（空いてる＝明るめ、混んでる＝暗め）。手間: 小 / 効果: 大

**予想の正直さ**
- 「◯号車が空いてそう」は、いちばん低い号車を必ず言い切る。号車の差が小さい（例: 全部 3.0〜3.2）ときも言い切るので、外れたときの信頼が下がる → 差が 0.3 未満なら「どの号車も同じくらい。空いてる時間帯は…」に切り替える。手間: 小 / 効果: 中
- ★1 の号車はマスがうすく点線（推定）になっていて区別はついている ＝ 良い

**通勤の憂うつ（根本に戻る）**
- 連続記録が途切れても責める言い方はない（「今日の1回目を記録しよう」）＝ 良い。疲れている人に圧をかけない方針は続ける
- メリット「乗る前の気持ちが少し軽くなる」→ 朝の通知の一言を、天気や曜日で変える（「金曜！あと少し」はもうある）。通知の本文はおすすめ号車だけなので、労いの一言も足す。手間: 小 / 効果: 小〜中
- メリット「つらかった日を誰かと分かち合える」→ ぎゅうぎゅうの報告が多い日に「今日は◯線みんなで戦った（◯人がぎゅうぎゅうを報告）」をふりかえりに。入力なし。手間: 小〜中 / 効果: 中

### 第 7 周（2026-10-03）視点: 画面読み上げ（視覚障がい）/ 機種変更・データ移行 / 通信量・電池
**画面読み上げ**（アクセシビリティツリーで確認）
- 号車ボタン「1号車」〜、記録ボタン「ガラガラ」〜、路線の操作ボタンに読み上げ用の名前がついている ＝ 良い。電車の図は「1号車 座れる、2号車 立つけど余裕…」とまとめて読み上げる ＝ 色が見えない人にも伝わる
- 記録後のメッセージは role=status で読み上げられる。気分スタンプは絵文字ボタンに「眠い」などの名前つき ＝ 良い
- メリット「結論を最初に聞ける」→ 電車の図の読み上げは全号車を順に読むので長い。見出し直後の一文「1号車・10号車 が空いてそう」が先に読まれる並びなので問題は小さい

**機種変更・データ移行**（コードで確認）
- 書き出し（app.js: JSON.stringify(data)）には共有番号（device）も入るが、読み込み（core.js: parseBackup）は routes / logs / memos / current だけを取り込む → 新しい機種では新しい番号になり、ランキング・「役に立った人数」・削除依頼の番号が引き継がれない
- Android は android:allowBackup="true" なので、Google の自動バックアップで設定ごと戻る可能性が高い。Web 版と iPhone では書き出し→読み込みが唯一の手段
- メリット「機種変更しても、自分の成績と仲間とのつながりが続く」→ parseBackup で device（文字列・64 文字以内）も受け取って引き継ぐ。手間: 小 / 効果: 小〜中
- プライバシーポリシーの「端末の中に保存」は、Android の自動バックアップ（本人の Google アカウントへの保存）に触れていない。気にする人向けに一言足すと誠実。手間: 小

**通信量・電池**
- アプリ本体は小さい（app.js 40KB・core.js 22KB）。いちばん大きいのは路線データ lines.json の 165KB で、初回にまとめて保存される（sw.js の FILES）。以後は通信しない ＝ 問題なし
- みんなの集計は 60 秒キャッシュ、ランキングと「役に立った人数」は 1 日 1 回 ＝ 通信は少ない
- 位置情報・常駐処理なし、通知は OS に予約するだけ ＝ 電池への影響はほぼない（ストアの説明で「電池を食わない」を言ってよい）
