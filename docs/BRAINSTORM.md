# 改善ブレスト（定期的に何周も回す）

根本: 通勤通学の時間が憂うつ → 小さな楽しみと便利さ。考える順番は必ず **メリット → それを叶える機能**（ユーザー指定）。
判断の軸: 入力を増やさない／ぱっと見でわかる／報告したくなる（＝空いてる号車の精度が上がる）。

## いまの意見まとめ（優先順）

1. **朝のラッシュに本物の報告が捨てられるおそれ**【コードで確認・今日入れた変更の副作用】IP ごとの上限（1 分 20 件、worker.mjs 24 行）は 429 を返し、アプリは 429 を「送り直さず捨てる」（app.js 236 行）。携帯回線は多くの人が同じ IP を共有する（キャリアグレード NAT）ので、朝 8 時台に同じ IP から 20 件を超えると、いたずらでない報告が黙って消える → ①IP の上限を 1 分 120 件程度に緩める ②「too_many」の 429 は捨てずに送信待ちに戻して後で送る（「too_soon」＝同じ号車の連投は今まで通り捨てる）。手間: 小 / 効果: 大（集計の土台）
2. **Android の「戻る」で、選択シートではなくアプリごと閉じる**【エミュレータで確認】路線選びのシート（picker）を開いて戻るボタンを押すと、シートが閉じずにホーム画面に戻る。Android の人は戻るでシートを閉じる癖があるので、選びかけの路線が消えて最初からやり直しになる → 公式の @capacitor/app を入れ、戻るボタンで「シートが開いていれば 1 段戻る／閉じる」、何も開いていなければ今まで通り閉じる。手間: 小（依存を 1 つ追加）/ 効果: 中〜大（Android の基本操作）
3. **片道だけ記録する人は「今月の目標」に一生届かない**【計算で確認】目標は毎月 30 回固定（core.js MONTH_GOAL）。平日は月 18〜23 日（2026-10: 21 日、2026-11: 19 日、2027-05: 18 日）なので、朝だけ記録する人・学生は毎日欠かさなくても達成できない → 目標を「その月の平日の数」（土日祝を除く、isOffDay で数える）にする。往復の人は 2 倍で余裕をもって届く。手間: 小 / 効果: 中（届かない目標はやる気を下げる）
4. **祝日にも「今日のおすすめ号車」の通知が来る**【コードで確認】リマインドは曜日ごとの毎週くり返し（core.js 245 行 schedule.on.weekday）なので祝日も鳴り、本文は平日の予想 → 休みの日に通勤の通知は憂うつのもと。毎週くり返しをやめ、起動のたびに「次の 2 週間の平日」を日付指定で入れ直す（祝日を飛ばせる）。通知の入れ直しは起動時と記録後にもうしている（refreshReminder）。手間: 小〜中 / 効果: 中
5. **「今日のおすすめ（時間帯）」が記録 1 回でも言い切る**【画面で確認】「16:45台 平均 2.0・1回 いつもより 3.0 空き」のように 1 回の記録で大きな差を出す（core.js recommend に回数の下限なし）。見出しも上の「空いてる号車」の「おすすめ」と紛らわしい → 見出しを「空いてる時間帯」に、2 回未満の枠は出さないか「まだ 1 回」と添える。手間: 小 / 効果: 中
6. **遅延の日の情報が誰にも届かない**【コードで確認】遅延・雨の印つきの記録はサーバーに送らない（reportPayload が null を返す）。遅延の日こそ空いてる号車と「いま遅れてるらしい」が知りたい → 遅延の印だけは「◯線・方面で遅延の報告」として送り、直近 30 分に 2 人以上いれば空いてる号車の欄に「遅延の報告 ◯人」と出す（集計の平均には入れない）。手間: 中 / 効果: 中〜大
7. **利用の伸びを見る手段がない**【コードで確認】サーバーのログ（observability）はあるが、「1 日の報告数・路線ごとの件数・端末数」を見る手順がない（package.json にも server にも集計用のコマンドなし）。どの路線から宣伝するか・効果が出たかを判断できない → `npm run stats`（wrangler d1 execute で数本の SELECT）を 1 つ用意し、docs に読み方を書く。個人が分かる情報は出さない。手間: 小 / 効果: 中（ユーザーの判断材料）
8. **ストアのスクリーンショットに一言の見出しがない**【画像で確認】3 枚とも画面そのまま。ストアでは 1 枚目を数秒しか見ないので、何のアプリか伝わりにくい → 画面の上に帯で「何号車が空いてる？ひと目でわかる」「乗ったらワンタップ」「毎月のバッジとふりかえり」を重ねた版を作る（canvas で合成、前回のフィーチャーグラフィックと同じ方法）。差し替えはユーザー。手間: 小 / 効果: 中〜大（インストール率）
9. **「今はしない」を選んだ人には二度と共有をすすめない**【コードで確認】共有のお願いカードは data.share が未設定のときだけ出る（app.js 318 行）。最初の 1 回で断ると、アプリの良さが分かったあとでも再提案がない（データ欄の奥のチェックだけ）→ 記録 20 回目に 1 度だけ「みんなの報告があると、乗ったことのない号車・時間も分かります」と再提案（断ったら以後出さない）。入力は増えない。手間: 小 / 効果: 中（共有する人が増える＝予想が当たる）
10. **金曜の終電が「休日」の集計に入る**【実行して確認】土曜 0:30 の記録は isOffDay = true、報告の daytype = "we"。鉄道のダイヤは深夜まで前日扱いなので、金曜の終電（平日ダイヤ）が休日の集計に、日曜の終電（休日ダイヤ）が平日に混ざる → 4 時より前の記録は前日として平日/休日を判定する（運行日の考え方）。手間: 小 / 効果: 小〜中（終電・夜勤の人には大）
11. **祝日の一覧が 2027 年で切れても誰も気づかない**【コードで確認】2028 年になると祝日がまた平日扱いに戻るが、エラーも出ない → 「今日の日付が一覧の最後の年を超えたら失敗するテスト」を 1 本置く（毎年の更新を忘れない仕組み）。手間: 小 / 効果: 小（保守）
12. **文字を大きくすると、結論の一文が途中で割れる**【エミュレータで確認・文字サイズ 130%】「1号車・10号車 が空い／てそう」と単語の途中で改行。号車のマスも「10」がマスの幅いっぱい。連続記録は「（今日／はまだ）」で割れる → 「が空いてそう」を折り返さないまとまりにし、号車番号は 2 桁で文字を少し小さく。手間: 小 / 効果: 小〜中（文字を大きくしている人＝高齢の人に多い）
13. **ダークモードで「推定」の号車の数字が読みにくい**【エミュレータで確認】★1 の号車はマスを半透明（opacity .55）にしているため、暗い背景では茶色が沈み、白い号車番号のコントラストが落ちる（2〜9 号車がほぼ読めない）。報告が少ない最初の数週間は全部この状態 → ダークモードでは半透明をやめ、点線の枠だけで「推定」を表す（または透明度 .8 に）。手間: 小 / 効果: 中

## 周回ログ

### 第 1 周（2026-10-03）視点: 初めて開いた人 / 毎日乗る会社員（3 か月目）/ 運用・サーバー
**初めて開いた人**
- メリット「30 秒で自分の路線の空いてる号車が見える」→ 初回だけ路線選びを自動で開く。いまは「いつもの路線」（路線情報なし）のまま推定が一般論しか出ない
- メリット「何両編成か知らなくても正しくすすめてくれる」→ 路線選択の最後に両数を聞く（候補ボタン）。いまは乗換メモの画面の中でしか変えられない（コードで確認: app.js の memo ステップ）
- メリット「いきなり同意を求められない」→ 共有のお願いカードは 1 回記録したあとに出す（いまは最初から一番上に出る）

**毎日乗る会社員**
- メリット「開かなくても答えと報告が済む」→ 通知にアクションボタン（ガラガラ／ふつう／混んでる）。朝の一言通知（実装済み）と組み合わせると、通知だけで完結する
- メリット「並ぶ場所まで迷わない」→ 号車だけでなく乗車位置（ホームの番号）。駅ごとのデータが必要で重い → 乗換メモで代替し、需要を見て
- メリット「帰りも同じ手間で使える」→ 時間帯で行き/帰りの路線自動切り替え（実装済み）。帰りの路線の追加を初回に促す

**運用・サーバー**
- 閲覧記録（views）はアプリを開くたびに 1 回書き込む。D1 無料枠は 1 日 10 万書き込み → 1 日 1 万人 × 数回までは大丈夫。超えそうなら「1 端末 1 日 1 枠 1 行」はそのままに、書き込みを 1 日 1 回にまとめる
- 報告が少ない路線は推定のまま → ローンチは路線を絞る（宣伝の話。アプリ側は路線ごとの「報告の集まり具合」表示で後押し）

### 第 2 周（2026-10-03）視点: 学生 / 子連れ・ベビーカー・車いす / 圏外・オフライン（地下鉄）
**学生**
- メリット「友だちと同じ号車で会える／待ち合わせが楽」→ 空いてる号車の欄に「LINE で送る」（例:「明日 7:40 の 7 号車で」）。Web は navigator.share、アプリは @capacitor/share の追加が必要。手間: 中 / 効果: 中（口コミで広がる入口にもなる）
- メリット「試験期間は空き方が違うのを知りたい」→ 試験・休暇モードは「くわしく」に移した。年数回しか使わないので位置としては妥当。季節で自動提案（2月・7月に一言）は余地あり。手間: 小 / 効果: 小
- メリット「ランキングで友だちと競える」→ 路線ランキングは実装済み。友だち同士の比較は ID 交換が要り入力が増えるので見送り

**子連れ・ベビーカー・車いす**
- メリット「エレベーターに近くて、空いている号車がわかる」→ 乗換メモの「エレベーター」タグはもうある。設定で「ベビーカー・車いす優先」を 1 回オンにすると、おすすめを「エレベーター近く × 空いてる」で選ぶ。データは自分のメモだけなので、メモがない人には効かない。手間: 小〜中 / 効果: 中（必要な人には大）
- メリット「優先席・フリースペースのある号車を知りたい」→ 車両ごとの設備データが要る。公開データが見当たらないので、みんなの報告に「フリースペースあり」を付けられる案。入力が増えるので保留

**圏外・オフライン（地下鉄）**
- 記録は端末に保存し、報告は送れなくても次に通信できたとき送る（online / 画面復帰で再送）＝ コードで確認、問題なし
- メリット「圏外でも表示を信じていいか分かる」→ みんなの集計が取れないと、黙って自分の記録と傾向だけの表示に戻る。根拠の一文（「みんなの報告 ◯件…」）が消えるだけなので、気づけない → 取れなかったときは「いまは圏外のため、あなたの記録と一般的な傾向だけで表示」と一言。手間: 小 / 効果: 小〜中

**アクセシビリティ（画面で確認）**
- 押せる部分の高さが 44px 未満のものがある（号車 40px、「くわしく」32px、「◯両編成（変える）」36px）。凡例は 12px でうすい灰色 → 上の意見まとめ 4 へ

### 第 3 周（2026-10-03）視点: 3 か月使った人 / プライバシー重視の人 / 競合アプリとの違い
**3 か月使った人**
- メリット「長く使っても目標がある」→ 称号は 3000pt で終わり（core.js の TITLES）。1 日 2 回・号車つき・連続ボーナスで月 800pt 前後 → 約 3.5 か月で頭打ち。月ごとにリセットされる「今月の目標」と季節バッジ（桜・梅雨・年末）で、ずっと目標が続く。手間: 小 / 効果: 中
- メリット「自分の通勤が良くなった実感」→ ふりかえりに「先月より空いてた回数 +3」のような前月比を 1 行。手間: 小 / 効果: 小〜中
- メリット「画面が長くて下まで見ない」→ 下の「今日のおすすめ（時間帯）」「曜日×時間の傾向」は v1 の機能で、いまの主役（号車）と離れている。たたむか、空いてる号車の欄に「15 分ずらすと ◯号車まで空く」と一言でまとめる。手間: 中 / 効果: 中

### 第 14 周（2026-10-03）視点: 携帯回線の人（ラッシュ時の通信）/ 1 年使った人のデータ量 / 権利表記
**携帯回線の人**（コードで確認）
- 日本の携帯回線はキャリアグレード NAT で、多くの端末が同じ公開 IP を共有する。今日入れた「同じ IP から 1 分 20 件まで」は、利用者が増えた朝のラッシュに正規の報告まで止める可能性がある
- しかもアプリは 429 を送り直さない（app.js: 5xx だけ送信待ちに戻す）ので、止められた報告は消える。利用者からは見えない
- メリット「報告がちゃんと届く」→ 上限を緩める（例: 1 分 120 件）＋「too_many」は送信待ちに戻す。同じ号車の連投（too_soon）は今まで通り捨てる。手間: 小 / 効果: 大

**1 年使った人のデータ量**
- 1 日 2 回 × 1 年 ≈ 500 件。以前の計測（5000 件 = 249KB、読み込み 61ms）から見て、数年分でも問題なし。予想は直近 90 日・号車は半減期 30 日なので、古い記録が判断をゆがめることもない ＝ 問題なし

**権利表記**
- 路線データは国土数値情報（CC BY 4.0）。画面の下に出典を表示している（アプリ版も同じ画面）＝ 問題なし
- 祝日は内閣府の公開データ。出典の表示義務はないが、コードのコメントに出典あり ＝ 問題なし
